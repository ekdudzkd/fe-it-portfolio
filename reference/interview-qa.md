# 동글서울 — 면접 꼬리 질문 대비

장표(`index.html`) 담당 역할에 쓴 내용마다 면접관이 이어서 물을 만한 질문과 답의 뼈대.
숫자 출처: 측정 기록 · MR 본문 (!1940 · !1960 · !1962 · !1972 · !1990 · !2039 · !2093 · !1726).
답은 내 말로 다시 다듬어 연습할 것.

## ① 로딩 성능

**Q. 62%는 어떻게 쟀나요?**
- 운영 빌드를 실제 Chrome(GPU)에서 열고, 부팅 구간마다 `performance.mark / measure` 를 심었다.
- CDP(Chrome DevTools Protocol) 스크립트로 캐시 비움 3회 · 캐시 있음 3회 반복. 100%까지 약 11.5~12.2초 중 `new World()` 가 7.2~8.1초.

**Q. 측정값이 흔들리지 않았나요?**
- 흔들렸다. 노트북이 배터리면 CPU가 3~4배 느려져 충전 중에만 쟀다.
- 전 / 후 빌드를 번갈아 6쌍 측정. 날마다 PC 속도가 달라 코드가 안 바뀐 구간(`world` 마크)으로 보정했다.
- 헤드리스에서 창이 가려지면 rAF 가 안 와서 `--disable-features=CalculateNativeWinOcclusion` 이 필요했다.

**Q. "빌드 때 굽기"가 정확히 뭔가요? 왜 통째로 굽지 않았나요?**
- 땅 칸마다 종류(잔디 · 길 · 물…)를 판정하는 계산을 Vite 플러그인이 빌드 때 Node 로 미리 돌려 52KB 바이너리로 배포.
- 원본 데이터의 지문(해시)이 다르면 그 자리에서 다시 계산 → 데이터를 고치고 굽기를 잊어도 깨지지 않음.
- 섬 전체 지오메트리를 통째로 굽거나 IndexedDB 에 캐시하는 것도 시험했지만, 지오메트리가 690MB라 쓰기 2~2.7초 · 읽기 0.6~1.9초에 충돌 · 함수 같은 저장 못 하는 상태가 많아 접었다. **작고 비싼 계산만 굽는 게 이득**이었다.

**Q. 인덱스 지오메트리로 왜 메모리가 줄었나요?**
- 상자를 합칠 때 꼭짓점이 면마다 복사돼 정점 1,520만 개 중 고유한 건 500만(33%)뿐이었다.
- 같은 정점을 한 번만 두고 인덱스 버퍼로 가리키게 바꿔 690 → 440MB, 로딩 10.0 → 9.3초.
- 정점색 · 노멀이 같은 정점만 합쳐야 모양이 안 바뀐다 → 펼쳐서 해시 비교로 2,701 / 2,703 동일 확인 (다른 2개는 움직이는 장식).

**Q. Float32Array 로 바꾸면 왜 빨라지나요?**
- 중간 JS 배열 · 객체를 만들지 않고 최종 버퍼에 바로 쓰니 메모리 할당 · GC 가 줄었다.
- three.js 와 같은 계산 순서로 써서 결과가 비트 단위로 같게 만들었다 → 섬 짓기 0.66~0.8배.

**Q. 아직 남은 병목은?**
- 건물 메시 만들기(프로파일 약 30%), 나무 · 꽃 약 200만 정점(InstancedMesh 후보), 지형 판정 일부.

## ② 화면 멈춤

**Q. 셰이더가 다시 컴파일되는 걸 어떻게 알았나요?**
- WebGL `linkProgram` 을 가로채 언제 · 어떤 셰이더(define 조합)가 링크되는지 기록했다.
- 밤이면 낮밤 코드가 그림자를 끄면서 재질 셰이더 55~60개가 새 조합으로 다시 컴파일됨. GPU 셰이더 캐시가 빈 첫 방문에서만 2.8초.

**Q. 처음에 셰이더 병렬 컴파일을 의심했다면서요?**
- `compileAsync` 로 이미 병렬이었고 0.2~0.3초뿐. 측정으로 가설을 버렸다.

**Q. GPU 업로드를 나누면 총 시간은 늘지 않나요?**
- 총 시간은 그대로다. 다만 로딩 화면이 도는 동안 약 60ms 묶음으로 나눠 올려서, 100% 뒤 타이틀이 3.3~3.9초 멈추던 게 없어졌다. **사용자가 체감하는 멈춤**을 없앤 것.

**Q. 길찾기를 Web Worker 로 옮기지 않은 이유는?**
- 길찾기가 월드의 충돌 · 길 데이터를 그대로 쓰는데, 워커로 넘기려면 그 데이터를 복사 · 동기화해야 했다.
- 제너레이터로 바꿔 메인 스레드에서 프레임당 4ms만 쓰게 하는 게 코드 변경이 작고 바로 효과가 났다 (2.36초 → 최대 0.19초). 찾는 동안 주민은 제자리 자세로 기다린다.

## ③ OSM 도로망

**Q. OSM 데이터를 그대로 쓰면 무엇이 문제였나요?**
- 같은 길이 여러 조각으로 겹치고, 다리 끝이 끊기고, 막다른 짧은 길이 많았다 → 변환 스크립트에서 8단계로 정리.
- 게임 맵 크기에 맞게 좌표를 변환하고, 랜드마크 · 퀘스트 목표 · 레이스 코스를 실제 경위도 위치로 다시 놓았다.

**Q. 중심선에서 차도 면은 어떻게 만들었나요?**
- 중심선에서 떨어진 거리로 차도 · 연석 · 차선 영역을 정하고(거리장), 교차로는 노드로 따로 처리, 정지선은 교차로 진입 지점에 생성.

**Q. 다리 상판이 왜 "한 덩어리 · 같은 곡률"이어야 했나요?**
- 조각마다 따로 만들면 이음새가 벌어지고 차가 튀었다. 하나의 곡선을 공유하게 만들어 이음새를 없앴고, 강둑에 비스듬히 놓이도록 임의 방향 상판 · 교각 · 진입로를 지원.

## ④ 트러블슈팅 (하늘색 화면)

**Q. 왜 테스트가 못 잡았나요?**
- 선언 안 된 이름은 JS 문법 오류가 아니라 실행할 때만 ReferenceError 가 난다. 빌드는 통과하고, 그 컴포넌트를 렌더하는 테스트가 없었다.

**Q. 정적 검사 테스트는 어떻게 만들었나요?**
- 소스 전체에서 선언 · import 되지 않았는데 쓰이는 이름을 찾는다. 브라우저 전역(window 등)은 허용 목록으로 관리.

**Q. ESLint `no-undef` 를 쓰면 되지 않나요?**
- 맞다. 프론트엔드에 ESLint 설정 자체가 없었다. 린트 도입은 팀 전체 코드에 경고가 쏟아지는 큰 작업이라, 이번에 샌 구멍(선언 안 된 이름)만 막는 가벼운 테스트를 먼저 CI에 넣었다.

**Q. 에러 바운더리는 어디까지 막나요?**
- 렌더 중 오류만 잡는다. 이벤트 핸들러 · 비동기 오류는 못 잡는다. 한 곳이 깨져도 앱 전체가 빈 화면이 되는 건 막는다.

## ⑤ 멀티 · 기타

**Q. 레이스를 왜 서버에서 계산했나요?**
- 클라이언트마다 프레임 · 지연이 달라 순위가 엇갈렸다. 서버가 진행 · 순위를 계산하고 WebSocket 으로 방에 알리면 모두 같은 결과를 보고, 보상도 서버가 판정해 조작을 막는다.

**Q. 실내 카메라에서 벽 반투명은 어떻게?**
- 카메라와 캐릭터 사이를 가리는 벽을 판정해 그 벽 재질만 반투명으로 바꾼다. (세부 방식은 코드 `frontend/src/game` 실내 카메라 모듈에서 다시 확인)
